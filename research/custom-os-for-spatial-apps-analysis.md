# Своя ОС для приложений класса God's Eye View — анализ

Вопрос: что нужно, чтобы написать операционную систему, в которой мы будем создавать
приложения и запускать продукт типа [God's Eye View](https://github.com/bilawalsidhu/gods-eye-view)
(см. `gods-eye-view-launch-data.md`).

## TL;DR

1. Чтобы **запустить** такой продукт, своя ОС не нужна: это веб-приложение (CesiumJS + WebGL),
   ему достаточно любого Linux с браузером. ОС — не техническое требование, а стратегическое решение.
2. «ОС с нуля» (ядро, драйверы, веб-движок) — нереалистично: GPU-стек и браузерный движок
   в сумме — десятки миллионов строк кода и сотни человеко-лет.
3. Реалистичный и общепринятый путь — **своя система на ядре Linux** по модели
   ChromeOS / Android / SteamOS: своё ядро продукта — это app-модель, SDK, системные сервисы
   и обновления, а не ядро ОС. Это 5–10 инженеров и 6–18 месяцев до v1.
4. Уникальность для нас — интеграция **Trinity**: ternary-акселератор (FPGA) как системное
   устройство для локального AI-инференса (BitNet) и t27-toolchain в составе SDK.
   Ни одна существующая ОС этого не даёт.

---

## 1. Что реально требует продукт типа God's Eye View

| Подсистема | Требование |
|---|---|
| Графика | GPU c OpenGL ES 3 / Vulkan; драйверы (Mesa); композитор; WebGL2 (CesiumJS), в идеале WebGPU |
| Сеть | TCP/IP, DNS, TLS 1.3, HTTP/2, WebSocket (live-фиды: OpenSky, ADS-B, AIS, USGS) |
| Runtime приложений | JS-движок + WebGL (браузерный) или нативный рендерер (Cesium Native, wgpu) |
| Хранилище | Кэш 3D-тайлов и TLE (гигабайты), быстрый доступ |
| Многозадачность | Планировщик, изоляция приложений, sandbox |
| Память | Стриминг фотореалистичных 3D Tiles ест 2–8 ГБ RAM |

Вывод: минимальная платформа = ядро Linux + Mesa + Wayland + браузерный движок.
Всё это существует в open source; писать с нуля нужно только то, что выше этого уровня.

## 2. Четыре уровня амбиций

### L0 — Киоск-образ (наша «ОС» в смысле ChromeOS-образа)
Buildroot/Yocto-образ: ядро Linux → cage (Wayland-киоск) → Chromium или WPE WebKit
в полный экран с нашим приложением. Загрузка сразу в продукт, как appliance.
- Команда: 1–2 инженера, 1–3 месяца.
- Это уже «своя ОС» продуктово: свой бренд, свой образ, свой апдейтер.

### L1 — Своя платформа приложений (рекомендуемый целевой уровень)
Модель ChromeOS: чужое ядро, свой мир поверх него.
- Свой композитор (Smithay/wlroots) и оконная модель.
- App-модель: приложения = web-пакеты (манифест, права, подпись); работают CesiumJS-приложения без переделки.
- Системные сервисы — главная ценность: **data-fusion daemon** (единая шина слоёв:
  самолёты, спутники, суда, камеры; кэш, rate-limit, реплей истории), гео-API, secrets-хранилище ключей.
- SDK + симулятор + документация; A/B OTA-обновления (RAUC / Mender / OSTree), verified boot.
- Команда: 5–10 инженеров, 6–18 месяцев до v1.

### L2 — Свой userland и нативный SDK
Замена браузерного runtime на нативный: Rust + wgpu (WebGPU), Cesium Native для 3D Tiles,
свой UI-toolkit или Flutter engine. Опционально микроядро (seL4) для критичных конфигураций.
- Команда: 15–30 инженеров, 2–3 года. Оправдано только после успеха L1.

### L3 — Полностью с нуля
Своё ядро, свои драйверы, свой веб-движок. Ориентиры масштаба: Linux ~40М строк,
Chromium ~35М, Mesa ~15М. Google Fuchsia — сотни инженеров и ~6 лет до первого продукта;
SerenityOS/Redox — годы работы сообществ без фотореалистичного 3D.
- Не рекомендуется: GPU-драйверы и веб-движок — два непроходимых для малой команды блокера.

## 3. Рекомендуемая архитектура (L1 с прицелом на L2)

```
┌─────────────────────────────────────────────────────┐
│  Приложения (web-пакеты: манифест + права + подпись) │
│  God's Eye View-класс, свои вертикали                │
├─────────────────────────────────────────────────────┤
│  SDK: JS API (гео, слои данных, AI) · позже Rust/wgpu │
├──────────────────────────┬──────────────────────────┤
│  Runtime: Chromium/CEF   │  Системные сервисы:       │
│  или WPE WebKit          │  data-fusion daemon,      │
│  (WebGL2/WebGPU)         │  tile-cache, keys, update │
├──────────────────────────┴──────────────────────────┤
│  Композитор (Smithay) · sandbox (ns/seccomp/portals) │
├─────────────────────────────────────────────────────┤
│  Linux LTS · Mesa · systemd/минимальный init · OTA   │
├─────────────────────────────────────────────────────┤
│  x86/ARM + GPU   ·   Trinity ternary-акселератор     │
│                      (FPGA, PCIe/USB): драйвер +     │
│                      runtime BitNet-инференса, t27   │
└─────────────────────────────────────────────────────┘
```

Выбор runtime: Chromium/CEF — полный WebGPU и совместимость, но тяжёлые security-патчи;
WPE WebKit — создан для embedded-киосков, легче, WebGL2 достаточно для CesiumJS.
Начать с Chromium (скорость), держать WPE как план Б.

Интеграция Trinity — то, что отличает нас от «ещё одного дистрибутива»:
- драйвер/runtime ternary-акселератора как системного compute-устройства;
- локальный AI-инференс (BitNet LLM) для аналитики слоёв без облака — критично для
  OSINT/оборонных заказчиков (air-gapped развёртывания);
- t27 → ядра для акселератора как часть SDK.

## 4. Команда и роли (L1)

| Роль | Кол-во |
|---|---|
| BSP/ядро/сборка образа (Yocto/Buildroot) | 1–2 |
| Графика: композитор, Mesa, интеграция движка | 1–2 |
| Runtime/браузерный движок, sandbox | 1–2 |
| Системные сервисы (data fusion, OTA, security) | 2 |
| SDK, документация, инструменты разработчика | 1–2 |
| Trinity-акселератор: драйвер + runtime | 1–2 (есть в команде) |

## 5. Риски

1. **Security-поддержка браузерного движка** — обязательные регулярные патчи; отставание = дыра.
2. **GPU-драйверы на нестандартном железе** — держаться Intel/AMD (открытая Mesa), избегать экзотики.
3. **Лицензии**: GPLv2 (ядро), LGPL (WebKit), BSD (Chromium) — совместимо, но нужна гигиена;
   ToS Google Map Tiles API (атрибуция, запрет офлайн-кэша сверх разрешённого).
4. **Регуляторика**: OSINT-продукт с военными слоями — экспортный контроль, санкционные списки.
5. **Скоуп-крип**: соблазн уйти в L2/L3 до того, как L1 принёс пользователей.

## 6. Первые шаги (Phase 0, ~4–8 недель)

1. Собрать Buildroot-образ: Linux LTS + Mesa + cage + Chromium kiosk на мини-ПК (Intel/AMD GPU).
2. Загрузка сразу в клон God's Eye View (источники данных — см. `gods-eye-view-launch-data.md`).
3. Прототип data-fusion daemon (Rust): OpenSky + CelesTrak + USGS → единый WebSocket для приложений.
4. Черновик app-манифеста (права: сеть, слои данных, камера) и подписи пакетов.
5. A/B-обновления через RAUC на двух разделах.
6. Параллельно: PoC подключения Trinity-FPGA как compute-устройства к образу.

Результат Phase 0 — загружаемый фирменный образ, «ОС» продуктово, и он же — скелет L1.
