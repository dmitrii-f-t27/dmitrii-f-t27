# TrinityOS на t27 «с нуля» — анализ и предложение среды

Вопрос: вся ОС/оболочка и приложения должны быть написаны на t27, без Linux.
Анализ сделан по фактическому коду репозиториев `gHashTag/t27` и `gHashTag/trinity`
(склонированы и изучены 24.08.2026).

## TL;DR

1. **Половина фундамента ОС уже существует.** TRI-27 — это готовое «ядро процессора»:
   27×32-бит регистров, 36 опкодов, 64КБ памяти, **Zig-эмулятор + Verilog на FPGA**,
   плюс спеки `vm-core`, `bus/pubsub`, `sandbox`, `file`, VSA — всё в .t27.
2. **Чего нет совсем: устройств.** У TRI-27 сегодня нет экрана, сети, ввода и часов —
   ни в эмуляторе, ни в RTL. ОС без I/O невозможна; первый шаг — контракты устройств в .t27.
3. **Роль Linux — честно.** Весь код ОС и приложений — 100% .t27. Linux остаётся только
   там же, где уже живут yosys/nextpnr/Zig: **хост для инструментов разработки** на время,
   пока TRI-27-железо растёт. Это не компромисс архитектуры, а станок, на котором точат деталь.
4. **Границы физики.** Фотореалистичный глобус God's Eye View (Google 3D Tiles, гигабайты,
   GPU-терафлопсы) на 64КБ ternary-VM невозможен и не нужен как цель. Наша цель —
   **своя векторная тактическая карта** + AI-аналитика слоёв (VSA/BitNet — родная сила
   ternary). Фотореализм — опциональный внешний рендерер, не часть ОС.
5. **Предлагаемая среда — Trinity Workbench**: эмулятор TRI-27 с устройствами + окно-обсервер
   (готовая база: `t27/apps/desktop`, Svelte) + hot-reload спек + golden-тесты.
   Тот же образ ОС без изменений грузится на QMTech FPGA, когда доходит до железа.

## 1. Что уже есть (инвентаризация по коду)

| Слой ОС | Артефакт в репо | Статус |
|---|---|---|
| CPU/VM | `trinity/src/tri27/emu/*.zig` (lexer, decoder, executor, loader), Verilog-таргет | Работает |
| ISA | 27 регистров, 36 опкодов, 64КБ памяти, `.tri` спека ISA | Работает |
| Язык/компилятор | `t27c`: 747 `.t27` спек → **Verilog / Zig / C** (28 модулей на софт-бэкендах) | Работает |
| Шина сообщений | `t27/specs/bus/pubsub.t27` + `bus/schema.t27` (топики, wildcards, подписки) | SPEC |
| Изоляция | `t27/specs/sandbox/*` (session timeout и др.) | SPEC |
| Файлы | `t27/specs/file/operations.t27`, `watcher.t27` | SPEC |
| AI-подсистема | VSA ops, BitNet inference (`trinity`), GF16 | Работает |
| Подпись пакетов | `t27c seal` — 729 запечатанных артефактов | Работает |
| FPGA | yosys→nextpnr→prjxray на QMTech XC7A200T, измеренные результаты | Работает |
| UI-заготовка | `t27/apps/desktop` — Svelte chat UI оркестратора | Есть база |

Вывод: **не нужно «начинать с нуля» — нужно достроить 4 недостающих слоя**:
устройства → ядро ОС → оболочка → SDK приложений.

## 2. Чего нет (и что это значит)

1. **Устройства (критично, блокер №1).** Ни дисплея, ни сети, ни ввода, ни часов.
2. **Ядро ОС**: планировщик, аллокатор, загрузчик модулей.
3. **Оболочка**: то, в чём живёт пользователь и запускаются приложения.
4. **SDK приложений**: манифест, права, жизненный цикл.
5. **Память**: 64КБ на всё. Только 7 000 самолётов OpenSky (lat/lon/alt/id) — уже ~100КБ.
   Нужна банковая память или рост адресного пространства в ISA (спековое изменение TRI-27).

## 3. Архитектура TrinityOS (всё — .t27 спеки)

```
Ring 3  Приложения (.t27 модули + манифест прав + t27c seal)
        worldmap · shell-apps · агенты
Ring 2  Оболочка: REPL/лаунчер, композиция окон-слоёв
Ring 1  Ядро ОС: планировщик (кооперативный), аллокатор,
        шина сообщений (есть: bus/pubsub.t27), загрузчик + верификация seal
Ring 0.5  Контракты устройств (MMIO, .t27 спеки — НОВОЕ):
        DISP · NET · INP · CLK · STOR · AI(VSA/BitNet-сопроцессор)
Ring 0  TRI-27 ядро (есть: Zig-эмулятор + Verilog)
─────────────────────────────────────────────────────────
Носители Ring 0: (а) эмулятор на хосте — сейчас; (б) QMTech FPGA — далее
```

Ключевые решения:

- **Изоляция без MMU**: одно приложение = один инстанс TRI-27 VM. В эмуляторе
  инстансы дёшевы; на FPGA — маппинг на PE/ядра mesh (`tt-trinity-gamma` — 32 PE).
  Обмен — только через шину (pubsub) и устройства, по правам из манифеста.
- **DISP — дисплей-лист, не пиксельный фреймбуфер**: VM пишет команды
  (`LAYER/POINT/LINE/TEXT/CLEAR`) в кольцевой буфер MMIO. 64КБ хватает на
  тысячи примитивов; рендер общий у носителя (Canvas в обсервере, HDMI-скан на FPGA).
  Это и есть «своя графика» уровня тактической карты — без GPU.
- **NET — мост с узким протоколом**: VM говорит `GET topic → записи фиксированного
  формата` (например, `QUAKES`, `ADSB bbox`). TLS/DNS/HTTP живут в мосте
  (сгенерированный C/Zig — тоже из .t27 спеки `interop`), на FPGA мост — softcore/сопроцессор.
  ОС не притворяется, что TLS-стек на 64КБ возможен — она его выносит в устройство,
  как реальные системы выносят его в NIC/модем.
- **AI как устройство**: VSA-операции и BitNet-инференс — сопроцессор с MMIO-очередью.
  Это уникальность платформы: аналитика слоёв (аномалии в трафике судов/бортов)
  на ternary — то, чего нет ни в одной ОС.

## 4. Среда разработки: Trinity Workbench

То, «в чём удобно работать» каждый день:

1. **`tri os run`** — эмулятор TRI-27 + устройства, поднимает WebSocket.
2. **Обсервер** (расширение `apps/desktop`): окно с рендером DISP-слоёв, лентой шины,
   состоянием регистров/памяти, кнопкой пошагового исполнения. Это «монитор» нашей ОС.
3. **Hot-reload**: правка `.t27` → `t27c gen-zig` → перезапуск VM с сохранением
   состояния устройств (секунды, не минуты).
4. **Golden-тесты**: каждое устройство и сисвызов — конформанс-векторы как уже
   принято в `conformance/` (та же культура, что FORMAT-SPEC-001).
5. **Один образ — два носителя**: тот же ROM грузится в эмулятор и на QMTech
   (DISP → HDMI, NET → UART/Ethernet-мост). Ничего не переписывается.

Рабочий цикл: пишем спеку → `tri test` → смотрим в обсервере → seal → на FPGA.

## 5. Путь к продукту класса God's Eye View на TrinityOS

| Этап | Что появляется | Оценка |
|---|---|---|
| **M0** | Спеки устройств DISP/NET/CLK/INP + эмуляция в Zig + обсервер рисует слои | 1–2 нед |
| **M1** | Ядро: планировщик, загрузчик+seal, шина (pubsub) между двумя VM | 2–4 нед |
| **M2** | Оболочка + приложение **worldmap**: векторная карта мира, слой USGS-квейков и OpenSky через NET-мост | 2–4 нед |
| **M3** | AI-устройство: VSA-аномалии по слоям; банковая память (спековое изменение ISA) | 4–8 нед |
| **M4** | FPGA-порт: DISP→HDMI на QMTech, NET-мост на softcore | квартал |

После M2 у нас есть демонстрируемая «ОС не на Linux»: загрузка → оболочка →
запуск приложения → живая карта с реальными данными, весь код — .t27.

## 6. Судьба ветки trinity-os/ (L0 на Buildroot)

Оставить как **отдельный трек «носитель/витрина»**: это способ показать чужой
продукт (God's Eye View) на своём железе уже сейчас и позже — корпус, в котором
живут эмулятор TrinityOS и NET-мост. Ядром стратегии он не является; если решите
— можно удалить с ветки одним коммитом.

## 7. Риски

1. **64КБ и рост ISA** — самое инвазивное изменение (M3), затрагивает эмулятор и RTL.
2. **Соблазн пиксельного фреймбуфера** — тянет в GPU-гонку, которую выигрывать не нужно;
   дисплей-лист держит нас в области, где ternary+FPGA конкурентоспособны.
3. **NET-мост — граница доверия**: всё внешнее входит через одно устройство —
   это и удобно (аудит), и ответственно (мост должен быть таким же spec-first).
4. **Двойная поддержка Zig/C бэкендов** — держать паритет через конформанс-векторы.
